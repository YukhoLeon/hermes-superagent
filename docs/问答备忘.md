# 问答备忘：搭建过程中问过的问题和答案

> 按时间顺序，每条尽量一两句话。细节见 README 和 Hermes 本机文档。

## 2026-11-09 搭建

**Q：dsh 是什么？卡兹克的 superagent 在哪？**
dsh 是 DeepSeek Harness。文章是 DeepSeek 的《Super-agent 设计探索》，原型是 deepseek-ai/dsh-superagent-prototype。卡兹克的项目叫 agent-autoloop，不叫 superagent，他明说借鉴了这篇文章和 Pi 的极简内核。

**Q：要不要从零写一个 Super-agent？**
不要。Hermes 的 Kanban、Profile、Gateway、Plugin、Cron 已经覆盖了八成机制。我们加的是制度：SOUL 纪律、授权头、收权、看门狗、observe 模式。

**Q：/sa 发出去飞书回"Unknown command"。**
网关在交给任何插件钩子之前先处理斜杠命令，未注册的直接拒绝。斜杠命令必须用 `ctx.register_command` 注册；不带斜杠的"派单"才走 `post_gateway_admission` 钩子。

**Q：可以关机明天再来吗？**
可以。看板、卡片、cron 都在文件里。网关是本机进程，关机即停，开机后计划任务拉起。cron 的漏跑会补一次。

## 2026-11-10 理解与调整

**Q：auto_decompose 是不是把 planer 的拆分职能拿走了？**
是一半。聊天里直接对 planer 说，planer 自己拆；进 triage 列的卡由内置拆分器拆，不经 planer，它只在所有子卡完成后作为根卡所有者被叫醒。已改：auto_decompose 关掉，不指名的活默认交 planer。

**Q：有张卡没有授权头？**
进了 triage 后被内置拆分器整篇重写了正文。根因同上，改了之后不再发生。

**Q：工人要扩权或要资料，找我还是找 Router？**
工人只能 `kanban_block` 提一个问题。通知顺着卡的订阅走：planer 在聊天里建的卡是 notify+wake，planer 被叫醒转述；sa-gate 建的卡是 notify，消息直达你。扩权要开新卡、写新授权头，不在原卡追加。

**Q：今天停、明天再做怎么操作？**
没开始的卡 `hermes kanban schedule <id>`；在跑的先 `reclaim` 再 `schedule`；在 dashboard 把 running 拖到 blocked 也行。代价都一样：本次运行进度丢失，明天从头跑。快做完的让它跑完再关。

**Q：sa-gate 到底有什么用？飞书自带的不是覆盖了吗？**
重叠八成。它独有的只有零 token 和自动盖授权头。平时用自然语言对 planer 说话，这两点都用不上。已禁用，代码留作以后接 GitHub 等自动来源的快速路径模板。

**Q：能否通过飞书让 planer 暂停任务，等跑完就停，直到我开口或定时恢复？**
能。planer 有 `kanban_schedule`、`kanban_unblock` 和 cronjob 工具。没有"调度器总开关"，暂停是按卡做的。

**Q：说"那张 1688 的单要顺丰"，系统能识别是哪个 thread 并转给工人吗？**
能。planer 用 `kanban_list` 按标题找卡，然后 `kanban_comment`。排队中的卡开工时读到；运行中的卡每 6 秒轮询新评论并当场注入；已完成的卡建新子卡接着做。

**Q：worker 会不会上下文溢出？我对 planer 多轮指示怎么处理？**
worker 每张卡一个会话，有自动压缩和迭代上限，超限就结束本次、下次尝试能读到上次做到哪。长任务应拆成多张有先后关系的卡。planer 的会话也会压缩，但它把每轮指示翻译成评论或新卡，看板才是记忆。对 planer 下指令时点名卡片，比说"刚才那个"可靠。

**Q：内置拆分器根据什么拆？复用它还是抄进 planer？**
提示词写死在 `hermes_cli/kanban_decompose.py`：输入是卡的标题正文、profile 名单及描述、兜底接单人；输出 2 到 6 张卡的 JSON 图。planer 已被 Hermes 注入编排手册，重合大半。只把它独有的四条规则抄进 planer 的 SOUL，再加"多卡拆分要留一张汇总卡给自己收口"。拆分器保留，作批量粗拆用。

**Q：要不要把微信和飞书都接进 planer？**
不要。planer 是故意削弱的调度员，不适合随手问事。微信接默认 Hermes 当私人助理，飞书接 planer 当工作入口。给默认 Hermes 开 kanban 工具，大活可以从微信流进看板。

**Q：Bots 和看板有什么不同？**
Bots 是把 profile 包装成"同事"的聊天界面：永久对话、例行任务、群聊、Bot 互发消息。看板是工单系统：排队、自动派人、重试、留痕。Bots 像会议室，看板像流水线。群聊出方案，看板出交付物。给正在干活的工人下指令要走评论，不要走 Bot 私聊。

**Q：我们这套比 Kanban 多做到了什么？**
机制上没有。blocked 通知、planer 评论工人、评论注入、重试、审阅通道都是 Hermes 原生。我们加的是制度：角色纪律、授权头、收权、observe、只在需要时开口。DeepSeek 设计里我们和 Hermes 都没做的：推断式候选、策略版本重校验、GitHub 来源、投机执行、云端循环。

**Q：/sa 和派单该保留吗？**
不必。已禁用，代码留在起步包里。

**Q：参考 hezberg 项目还有什么可改进的？**
他强在产品化外壳（安装升级回滚、doctor、带去重退避的提醒账本、双信号卡死检测）。我们强在已端到端跑通、三个专长工人加审阅闸门、Router 保留 cron 能调度暂停、中途评论直达已落地。最值得补的是看门狗的去重退避和心跳检测。

**Q：我改过的看门狗和他比如何？**
已覆盖他的主要优势：同批去重、6 小时重提、Kanban 已推送过的卡延后 6 小时、清空收尾，"避开原生通知重复"这点比他好。唯一差距是卡死检测按开始时间算，已改为按最近一次心跳或评论计时，30 分钟无活动才点名。
