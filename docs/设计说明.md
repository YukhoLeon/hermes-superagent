# 设计说明：Super-agent 的概念、它在 Hermes 里的对应物、以及参考资料

> 这份文档讲"为什么这样设计"。部署看 README，日常使用看《使用说明》，踩坑看《运维与排错》。

## 1. 三份参考资料分别讲了什么

### 1.1 DeepSeek 的《Super-agent 设计探索》与 dsh-superagent-prototype

dsh 就是 DeepSeek Harness（DeepSeek 自家的 agent 框架）。文章的出发点是：**人的注意力才是多任务的瓶颈**，所以 agent 要"少占人注意力，多交付价值"。为此提出：

| 概念 | 说人话 |
|---|---|
| **Router / Worker 双层** | 一个常驻的"调度员"只负责接单和派活，不自己干；多个互不干扰的"工人"各干一张工单。调度员用便宜模型，工人用最强模型。 |
| **Trigger 与两级过滤** | 聊天、@、Issue、CI 结果都是"触发"。先用代码规则（白名单、来源）过滤掉大部分，剩下的才让模型判断要不要接。 |
| **Ticket + Mandate（工单 + 授权）** | 接下的活变成工单；每张工单带一个不可变的"授权头"：谁要的、凭什么、允许做到哪。 |
| **订阅直通** | 工人开工后直接订阅那个话题，后续追问直达工人，不再绕调度员。 |
| **observe → auto** | 不是明确请求、只是"看起来该做"的活，先只记录不执行（observe），人看过记录觉得对，再切成自动（auto）。 |
| **Watchdog** | 一个独立的定时检查者，看工人有没有卡死、空转。 |
| **按影响停下来** | 小改动做到可审阅为止；要做设计决策的，停下来只问一个问题。 |

原型（MIT 开源）是一个面向单个 GitHub 仓库的 coding agent：白名单里的人 @ 它，它开工单、在独立会话和 worktree 里干活、回 PR。它有一套 Runtime / Engine / Store / Effects 的严谨架构（单一写入者、事务内入队、提交后执行）。**这些架构细节不用自己写，Hermes 的看板内核已经做了等价的事**（SQLite、原子领取、事件表、崩溃回收）。

### 1.2 卡兹克的 agent-autoloop

他折腾一年后重写开源的"Agent 自动化中台"：约 1600 行零依赖内核加全部插件化（事件源 / Agent / 通知通道 / 交付）。他明说借鉴了 DeepSeek 的 Super-agent 文章和 Pi 的极简内核。四个值得抄的机制：

- **挂起零消耗**：等人审批时没有任何 agent 进程在跑。Hermes 看板的 `blocked` 状态就是这个：工人退出，卡片躺着，你回答后再拉起。
- **事件溯源**：只追加的账本，断电可恢复、不重复执行。看板的 `task_events` / `task_runs` 表就是账本。
- **指令与数据分离**：Issue 正文、网页内容只当资料，不拼进指令。卡片模板里固定了"资料"段，并写进了每个角色的纪律。
- **跳数熔断**：agent 互相唤醒超过 8 层就止损。Hermes 有 `kanban.failure_limit`、`delegation.max_spawn_depth`、Bot 互发消息的 `max_hops: 4`，加上我们的规则"工人不再派工人"。

### 1.3 两个已经在 Hermes 上做了的社区项目

- **hezberg/hermes-superagent**：Router 是一个只有 kanban 工具的 profile，Worker 是看板工人，Gate 是白名单，Mandate 是卡片头部，Watchdog 是 cron 跑的脚本，accept mode 默认 observe。强在产品化外壳：一行安装、事务式向导、升级回滚、`doctor`、带去重退避的提醒账本。他的 Gate 和 Fast Path 截至 2026-11 仍是"逻辑实现、网关接线二期"。
- **hongyaok/hermes-SuperAgent-World**：一个插件，强调"零 token 路由"、"默认 observe"、"工人不提交，人类是唯一发布闸门"，带像素小镇可视化。

本项目走的是 hezberg 的路线（profile + 看板 + 少量脚本），全部用 Hermes 官方机制，没有新框架。

## 2. 概念对照表

| Super-agent 概念 | Hermes 里的对应物 | 本项目做了什么 |
|---|---|---|
| Router（调度员） | profile `planer` | SOUL 写成"只派不干"，工具收窄到看板和记忆，换便宜模型 |
| Worker（工人） | profile `coder` / `researcher` / `reviewer`，由看板调度器拉起 | 各自的 SOUL：汇报格式、范围边界、外部内容不当指令、三种合法收尾 |
| Ticket（工单） | 看板卡片，`kanban.db` 的一行 | 原生 |
| Assignment / 重试 | `task_runs`、崩溃回收、`max_retries`、熔断 | 原生 |
| Mandate（授权头） | 卡片正文第一段 | `templates/mandate.md`，Router 建卡时照着写 |
| Gate（准入） | `FEISHU_ALLOWED_USERS` / `FEISHU_GROUP_POLICY` | 配置为只允许你本人、群内需 @ |
| Fast Path（零 token 路径） | 插件斜杠命令或 `post_gateway_admission` 钩子 | `optional/sa-gate`，默认不启用 |
| Slow Path（模型研判） | planer 的正常聊天回合 | 原生 |
| 订阅直通 | 看板通知订阅；聊天建卡自动 `notify+wake`；运行中的工人每 6 秒轮询新评论 | 原生，写进了 Router 手册 |
| observe / auto | `kanban.auto_decompose` | 设为 false：triage 只记录不执行，不指名的活统一经 Router |
| Watchdog | 调度器自带失联回收、超时、stranded 诊断 | `scripts/sa_watchdog.py` 做汇总：去重、6 小时重提、避开原生通知重复、30 分钟无心跳点名 |
| 审阅闸门 | `kanban_request_review` 到 reviewer（`review_dispatch: true`，带 `sdlc-review` 技能） | 原生，写进 coder / reviewer 的 SOUL |
| 面板 | `hermes dashboard` 的 Kanban 页、桌面端 Kanban 与 Bots | 原生 |
| 成本分档 | 每个 profile 自己的 `model.default` | Router 用 sonnet，工人用强模型 |
| 上下文管理 | 自动压缩、`artifacts` 附件、`session_search`、跨次尝试交接 | 原生 |
| Source：GitHub | 网关 Webhook 适配器 | 未做 |
| 云端循环 + 本地 daemon | terminal backend（ssh / docker / modal） | 未做 |

一句话总结：**Hermes 提供了几乎全部机制，本项目加的是制度**。DeepSeek 设计里双方都还没做的：推断式候选、策略版本化重校验、GitHub 来源、投机执行、云端循环。

## 3. 架构（文字版）

```
飞书（Router 入口）/ 微信（默认 Hermes，大活可建卡）/ Cron ──► Gateway（白名单、@ 规则）
                                                                   │
                                                                   ▼
                                                    planer（Router：查重、建卡、写授权头、派人）
                                                                   │ kanban_create
                                                                   ▼
                                        ┌──────── Kanban 看板（kanban.db）────────┐
                                        │ triage → todo → ready → running → review → done │
                                        └───────────────┬─────────────────────┘
                                   调度器每 60 秒：领取 ready 卡 → 拉起 worker 进程
                                                        │
                                   ┌────────────┬───────┴────────┐
                                   ▼            ▼                ▼
                                coder       researcher        reviewer
                                   │            │                │
                            request_review   complete    complete / request_changes
                                   └────────────┴────────────────┘
                                                │ 终态事件
                                                ▼
                       通知订阅 → 回到发起的聊天（notify+wake 叫醒 planer 汇报）
                       看门狗 cron → 只在 blocked / review / 卡死 / 诊断时发一条
```

## 4. 几个关键取舍

- **为什么关掉 auto_decompose**：内置拆分器不经 planer、不加载它的 SOUL，会整篇重写卡片正文，授权头因此丢失。关掉后 triage 列变成 observe 区，不指名的活都经 Router 之手。拆分器保留给批量粗拆（dashboard 的 Decompose 按钮、`hermes kanban decompose --all`）。
- **为什么禁用 sa-gate**：它独有的只有零 token 和自动盖授权头；单人自然语言用法下，planer 用的是便宜模型且 SOUL 会写授权头，还会查重、反问、用自己的话汇报。代码留作以后接自动来源的模板。
- **为什么微信不接 planer**：planer 是故意削弱的，随手问事体验差。微信接默认 Hermes 当私人助理，飞书接 planer 当工作入口。
- **为什么 Router 保留 cronjob 工具**：这样"今天别派新活、明早九点恢复"planer 自己能办。
- **Bots 与看板**：Bots 是会议室（同步讨论），看板是流水线（异步工单）。群聊出方案，看板出交付物。给正在干活的工人下指令走评论，不走 Bot 私聊。
